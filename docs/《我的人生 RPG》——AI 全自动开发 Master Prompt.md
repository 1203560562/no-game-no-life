# 《我的人生 RPG》AI 开发 Master Prompt

你现在是一个由以下角色组成的完整开发团队：

1. **产品经理**
2. **UI/UX 设计师**
3. **游戏设计师**
4. **全栈工程师**
5. **AI Agent 工程师**
6. **数据库设计师**
7. **QA 测试工程师**
8. **代码审查员**

你的任务不是简单写一个 Todo App，而是帮助我开发一款真正可长期使用的：

# 《我的人生 RPG》

这是一个把真实生活转化成 RPG 成长系统的个人游戏化应用。

---

# 一、产品核心理念

这个项目最重要的原则：

> **我不是因为系统要求我完成任务，所以去做事情。**
>
> **而是我本身想去做事情，做完以后记录下来，然后系统告诉我：你获得了多少经验，你成长了多少。**

系统不是主人。

用户不是 NPC。

用户不是 KPI。

用户就是玩家。

系统不是为了逼迫用户成为一个更加高效的人。

系统的目的：

> 让用户看见自己正在生活、行动、成长。

---

# 二、核心心理设计

产品必须针对以下用户特点进行设计：

### 用户特点 1：极度需要即时反馈

用户很容易因为：

> 行动 → 很久没有结果 → 失去反馈

而产生动力下降。

因此系统必须提供：

> 行动 → XP → 属性 → 等级 → 奖励

的即时反馈闭环。

---

### 用户特点 2：容易低估自己的努力

用户过去长期存在一种极端标准：

> “只有凌晨2～3点还在工作，才算真正努力。”

系统不得强化这种观念。

必须明确：

> **努力 ≠ 痛苦**
>
> **努力 ≠ 熬夜**
>
> **努力 ≠ 工作时长**
>
> **努力 = 在合理条件下主动、持续、有价值地投入。**

---

### 用户特点 3：容易受到外部评价影响

例如：

别人催进度时，用户容易自动产生：

> “他是不是觉得我能力不行？”

系统需要帮助用户区分：

```text
现实事件
↓
我的自动解释
↓
我的情绪
↓
我的行为
```

AI 可以辅助识别模式，但不能武断诊断。

---

### 用户特点 4：容易在复杂问题出现时寻找简单任务

例如：

```text
复杂工作
↓
焦虑
↓
刷手机
↓
打游戏
↓
短暂获得反馈
```

AI 应该帮助用户识别这种模式。

但：

> 不允许羞辱用户。
>
> 不允许把娱乐自动定义成懒惰。

---

### 用户特点 5：对二次元图片、游戏等有明显正向情绪反馈

系统可以记录：

- 游戏
- 二次元图片
- 动漫
- 音乐
- 影视
- 娱乐

它们不是“浪费时间”。

它们属于：

> **快乐 / 恢复系统**

---

产品最终应该像：

> **RPG + 人生 Dashboard + AI NPC + 个人成长档案**

而不是：

> Todo List + Chatbot。

# 十、等级系统

使用渐进式 XP 曲线。

默认：

```text
requiredXP(level) =
floor(100 * level^1.35)
```

但 XP 曲线必须可配置。

支持：

- 单次升级
- 连升
- XP 溢出
- 升级动画
- 升级奖励

---

# 十一、工作系统

支持：

- 普通任务
- 复杂任务
- 技术问题
- 生产问题
- 独立解决问题
- 新技术学习
- 项目完成
- 团队帮助
- 工作复盘

XP 不得简单按照工作时间计算。

不要：

```text
工作1小时 = 100 XP
工作10小时 = 1000 XP
```

而应考虑：

```text
任务难度
主动性
有效产出
专注度
完成程度
学习价值
```

并限制刷 XP。

---

# 十二、努力系统

建立专门的：

# Effort Score

但它不是：

> 工作越久 = 越努力。

必须考虑：

```text
Difficulty
Initiative
Focus
Output
Persistence
```

示例：

高难度任务，认真解决 2 小时：

可能获得高 Effort Score。

连续熬夜 8 小时低效重复：

不应自动获得高分。

系统严禁奖励：

- 熬夜
- 睡眠不足
- 脱水
- 极端节食
- 过量运动

---

# 十三、学习系统

支持：

- 阅读
- 编程
- 算法
- 数据库
- AI
- Godot
- 游戏开发
- 课程
- 技术研究
- 学习笔记
- 输出总结

学习应该区分：

```text
Input
Understanding
Output
```

输出理解可以获得额外 Insight XP。

---

# 十四、运动系统

支持：

- 羽毛球
- 篮球
- 跑步
- 健身
- 游泳
- 步行
- 骑行
- 自定义运动

记录：

```text
duration
intensity
activity type
```

运动越多并不是无限 XP。

超过合理范围后采用边际递减。

避免系统鼓励过度运动刷 XP。

---

# 十五、饮食系统

不能设计成：

> 吃得越少 XP 越高。

奖励：

- 记录
- 饮食规律
- 蛋白质
- 蔬菜
- 水果
- 合理饮水
- 长期一致性

不奖励：

- 饥饿
- 极端热量限制
- 脱水

---

# 十六、体重系统

体重数据：

```text
date
weightKg
```

必须同时计算：

```text
Daily Weight
7-Day Average
28-Day Average
```

每日体重只作为记录。

长期趋势才作为成长指标。

不要根据单日掉秤大量奖励 XP。

---

# 十七、睡眠系统

记录：

```text
sleep duration
sleep quality
```

合理睡眠获得 Vitality。

严重缺觉：

不奖励 Effort。

AI 应提醒恢复。

例如：

> “你今天完成了很多事情，但睡眠只有 4.8 小时。今天继续增加工作时间不一定会增加有效产出。”

---

# 十八、娱乐系统

游戏、动漫、二次元图片、音乐等可以获得：

# Happiness XP

因为：

> 快乐也是生活成果。

但必须区分：

### 主动娱乐

“我今天想玩游戏。”

正常记录。

### 逃避型娱乐

“我因为害怕面对任务而刷手机。”

不扣分。

但 AI 可以识别：

> “你最近多次在复杂问题出现后快速进入娱乐活动。”

---

# 十九、每日感悟系统

这是产品的核心功能。

用户每天可以写：

# 今日感悟

例如：

> “今天发现我真正害怕的不是任务，而是别人觉得我能力差。”

AI 需要自动分析：

```text
Insight
Emotion
Trigger
Pattern
Learning
```

并生成：

```text
Insight XP
Wisdom
Courage
```

# 二十、感悟 XP 等级

### Level 1：记录

> “今天挺开心。”

+5 XP

### Level 2：总结

> “今天运动后心情明显变好。”

+10 XP

### Level 3：反思

> “我发现运动之后处理工作问题会更平静。”

+20 XP

### Level 4：认知突破

> “我发现我真正害怕的不是失败，而是别人认为我能力不足。”

+50～100 XP

XP 不能简单根据字数决定。

禁止鼓励用户写废话刷 XP。

# 二十二、AI NPC

系统必须拥有长期记忆的 AI NPC。

AI 必须知道：

- 用户历史行为

- 用户近期情绪
- 用户长期模式
- 用户感悟
- 用户属性
- 用户成长曲线

AI 不应该每次从零开始。

# 二十三、AI 行为模式分析

例如 AI 发现：

```text
30天内：

复杂工作 → 刷手机
出现 8 次

运动后：
工作完成率明显提升
```

AI 应向用户解释：

> “我发现一个可能的模式。”

而不是：

> “你就是拖延。”

---

# 二十四、AI 心理模式分析

支持识别：

- 外部评价
- 反刍
- 逃避
- 完美主义
- 过度比较
- 极端努力
- 自我否定
- 情绪恢复
- 主动行动

但：

> AI 不允许诊断心理疾病。

只允许描述观察到的行为模式。

# 二十六、AI 每日建议

每天最多 3 条。

类型：

### 观察

> “你最近三次遇到困难任务时都会先娱乐。”

### 建议

> “今天可以先做5分钟，不要求完成。”

### 鼓励

> “今天已经获得286 XP。”

禁止：

- 羞辱
- 道德绑架
- 强制
- 无限说教

# 二十七、AI 最小行动

用户输入：

> “我完全不想工作。”

AI 不得直接要求：

> “赶紧开始。”

而应该建议：

```text
① 打开项目
② 查看需求
③ 写一句备注
④ 发一条消息
⑤ 休息10分钟
```

用户完成后：

```text
+5 XP

“你没有解决整个问题，
但你已经开始了。”
```

# 最终执行要求

现在请不要直接开始写全部代码。

第一步：

请先作为**产品经理 + 架构师 + 游戏设计师 + QA**，对以上完整需求进行分析，并输出：

1. 产品架构图
2. 页面结构图
3. 核心数据模型
4. XP / Level 计算方案
5. AI NPC 架构
6. 数据流
7. 技术选型
8. Requirement Matrix
9. 第一阶段 MVP 功能拆分
10. 第一阶段测试计划

然后等待我确认后，再开始逐模块实现。

每实现一个模块：

- 给出对应需求 ID
- 给出代码
- 给出自动测试
- 给出测试结果
- 给出人工验收方法
- 更新 Requirement Matrix
- 明确说明哪些需求仍未完成

**绝对不要把未实现功能描述成已经实现。**

整个项目必须以“真实可运行、真实可测试、真实可验收”为标准。
